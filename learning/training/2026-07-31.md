### 2. slice 测试补强

一种完整写法如下：

```go
func TestSliceCopy(t *testing.T) {
	tests := []struct {
		name          string
		src           []int
		build         func([]int) []int
		want          []int
		checkAliasing bool
		wantShare     bool
	}{
		{
			name:          "assignment",
			src:           []int{10, 20},
			build:         func(src []int) []int { return src },
			want:          []int{10, 20},
			checkAliasing: true,
			wantShare:     true,
		},
		{
			name: "copy",
			src:  []int{10, 20},
			build: func(src []int) []int {
				dst := make([]int, len(src))
				copy(dst, src)
				return dst
			},
			want:          []int{10, 20},
			checkAliasing: true,
			wantShare:     false,
		},
		{
			name:          "append copy",
			src:           []int{10, 20},
			build:         func(src []int) []int { return append([]int(nil), src...) },
			want:          []int{10, 20},
			checkAliasing: true,
			wantShare:     false,
		},
		{
			name:  "empty",
			src:   []int{},
			build: func(src []int) []int { return append([]int(nil), src...) },
			want:  []int{},
		},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			src := append([]int(nil), tt.src...)
			dst := tt.build(src)

			if !slices.Equal(dst, tt.want) {
				t.Fatalf("dst=%v, want %v", dst, tt.want)
			}
			if !tt.checkAliasing {
				return
			}

			dst[0] = 99
			shared := src[0] == 99
			if shared != tt.wantShare {
				t.Fatalf("shared=%v, want %v", shared, tt.wantShare)
			}
		})
	}
}
```

需要在 import 中加入 `slices`。空 slice 用例明确检查长度和内容，但不检查别名，因为没有元素可修改；“没有 panic”本身不是充分断言。

两种表达式的结论：

- `dst1 := src[:0]`：`len(dst1)==0`，`cap(dst1)==cap(src)`，仍共享 backing array。只要容量足够，向 `dst1` 追加就可能覆盖 `src` 的已有元素。
- `dst2 := append(src[:0:0], src...)`：三索引切片把容量限制为 0。非空 `src` 追加时容量不足，因此结果需要新的 backing array，与 `src` 的元素存储独立。
- 当 `src` 为空时，没有元素可用于观察别名；不要把“非空时会分配”的结论机械套到空输入。

### 3. 滑动窗口不变量、走查与复杂度

**不变量：**进入内层收缩循环时，`counts[x]` 等于值 `x` 在闭区间 `[left,right]` 中出现的次数，`distinct` 等于该窗口中 `counts[x] > 0` 的不同值数量。

**收缩条件：**当 `distinct >= k` 时，当前窗口满足要求，因此先更新最短长度，再删除 `nums[left]` 并右移 `left`；循环结束时 `distinct < k`，当前窗口已经不满足要求，而刚刚删除元素之前的窗口是以当前 `right` 结尾的最短可行窗口。

对 `nums=[1,2,1,3], k=3` 的关键状态走查：

| 动作 | `left` | `right` | `counts` | `distinct` | `minlen` |
|---|---:|---:|---|---:|---:|
| 加入 `1` | 0 | 0 | `{1:1}` | 1 | 5 |
| 加入 `2` | 0 | 1 | `{1:1,2:1}` | 2 | 5 |
| 再加入 `1` | 0 | 2 | `{1:2,2:1}` | 2 | 5 |
| 加入 `3` | 0 | 3 | `{1:2,2:1,3:1}` | 3 | 4 |
| 删除左侧 `1` | 1 | 3 | `{1:1,2:1,3:1}` | 3 | 3 |
| 删除左侧 `2` | 2 | 3 | `{1:1,2:0,3:1}` | 2 | 3 |

所以答案是 `3`，对应窗口 `[2,1,3]`。

测试表增加：

```go
{"shrink with duplicate", []int{1, 2, 1, 3}, 3, 3},
```

复杂度证明：`right` 从 0 到 `n-1`，最多移动 `n` 次；`left` 只向右移动，也最多移动 `n` 次。每次移动只做均摊 `O(1)` 的 map 操作，因此总时间为 `O(n)`，不是 `O(n^2)`。map 最多保存输入中的不同值，空间复杂度为 `O(u)`，其中 `u <= n`。

### 4. handler 生命周期标准设计

当前代码的问题不是“goroutine 是否最终结束”，而是两个执行流都可能写同一个 `ResponseWriter`：

- 后台 goroutine 在 DB 成功后写 `202`，失败后写 `500`；
- handler goroutine 在 Kafka 失败后也可能写 `500`；
- handler 可能先返回，后台 goroutine 再写响应；
- 后台 DB 调用没有接收 `r.Context()`，客户端取消不会传播给它。

确定性失败时间线：

```text
handler goroutine     background goroutine          test goroutine
      |                        |                           |
      |-- start background -->|                           |
      |                        |-- signal ready --------->|
      |-- Kafka succeeds      |                           |
      |-- return ------------>|--------------------------> observe returned
      |                        |<--------- close release --|
      |                        |-- WriteHeader(202) ------> record late write
      |                        |-- signal done ----------->|
```

测试中 channel 的责任：

- `ready`：后台 goroutine 发送一次，表示已到写响应前；后台拥有发送责任。
- `release`：测试 goroutine 关闭，允许后台继续；测试拥有关闭责任。
- `handlerDone`：运行 handler 的 goroutine 在返回时关闭。
- `backgroundDone`：后台 goroutine 退出时关闭。

线程安全的记录器骨架：

```go
type responseEvent struct {
	kind string
	code int
	body string
}

type recordingWriter struct {
	mu     sync.Mutex
	header http.Header
	events []responseEvent
}

func newRecordingWriter() *recordingWriter {
	return &recordingWriter{header: make(http.Header)}
}

func (w *recordingWriter) Header() http.Header {
	return w.header
}

func (w *recordingWriter) WriteHeader(code int) {
	w.mu.Lock()
	defer w.mu.Unlock()
	w.events = append(w.events, responseEvent{kind: "status", code: code})
}

func (w *recordingWriter) Write(p []byte) (int, error) {
	w.mu.Lock()
	defer w.mu.Unlock()
	w.events = append(w.events, responseEvent{kind: "body", body: string(p)})
	return len(p), nil
}

func (w *recordingWriter) snapshot() []responseEvent {
	w.mu.Lock()
	defer w.mu.Unlock()
	return append([]responseEvent(nil), w.events...)
}
```

这里 mutex 保护测试记录，避免测试替身自身产生数据竞争。更严格时，`Header()` 返回的 map 也需要限制为单一所有者，或把 header 操作纳入同一同步方案。

测试控制骨架：

```go
ready := make(chan struct{})
release := make(chan struct{})
handlerDone := make(chan struct{})
backgroundDone := make(chan struct{})

// 被注入的后台依赖在准备写响应前执行：
// close(ready)
// <-release
// defer close(backgroundDone)

go func() {
	defer close(handlerDone)
	handler.ServeHTTP(writer, request)
}()

<-ready
<-handlerDone
before := writer.snapshot()

close(release)
<-backgroundDone
after := writer.snapshot()

if len(after) != len(before) {
	t.Fatalf("response was written after handler returned: before=%v after=%v", before, after)
}
```

实际的 `handlePostTask` 把 `DbService`、Kafka writer 和 `go func` 写死在函数内部，缺少同步点注入位置，因此很难直接写出稳定的单元测试。工程上应先把“创建任务”和“入队”抽成可替换的小依赖，或者把异步工作交给 handler 外部拥有的队列/worker；这不是为了 mock 而抽象，而是为了明确生命周期所有权。

推荐契约：

- handler goroutine 是 `ResponseWriter` 的唯一所有者，所有响应必须在 handler 返回前完成。
- 后台任务不能持有 `ResponseWriter`；它只接收不可变任务数据。
- 需要与请求同生共死的操作使用 `r.Context()`，所有阻塞点监听取消。
- 需要脱离请求继续执行的任务由服务级 worker 拥有，并使用服务生命周期 context，而不是偷偷复用请求资源。
- handler 返回前必须确定唯一 HTTP 状态；后台失败通过任务状态、日志或指标暴露，不能再次修改已经返回的 HTTP 响应。
