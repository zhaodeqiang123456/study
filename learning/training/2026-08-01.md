### 1. 证据边界复述

#### 1.1 `go test -race` 无报告，不能证明不会双写响应

结论：**尚未证明**。

race detector 检测的是运行期间发生的未同步内存访问。HTTP 的“一个请求只能形成一个一致响应”是协议和业务不变量，不是纯内存竞争问题。即使两个写入被 mutex 串行化，仍可能先写 `500`，随后又尝试写 `202`；这没有 data race，但响应语义仍错误。

当前代码的最小失败时序：

1. handler 启动 DB goroutine；
2. Kafka 写入失败，handler 调用 `http.Error(..., 500)` 并返回；
3. DB 插入随后成功，后台 goroutine 再调用 `WriteHeader(202)` 和 `Encode(task)`。

缺失证据是：响应事件次数、顺序以及 handler 返回后是否仍有写入。

#### 1.2 fake queue 的取消测试不能证明真实 Kafka 没有产生消息

结论：**尚未证明**。

fake 只能证明 handler 按 fake 的契约传递了 context，并正确处理 fake 返回的错误。真实 Kafka 调用可能在 broker 已接收消息后，客户端才因取消或超时返回错误。这时调用方看到失败，但消息可能已经存在，这属于分布式系统中的“不确定结果”。

最小反例：broker 已持久化消息，但确认响应在网络中丢失；客户端收到 timeout，重试后产生重复消息。因此 `taskID` 应作为幂等键，消费者不能依赖“发送返回错误就一定没消息”。

#### 1.3 goroutine 最终退出不能证明没有泄漏

结论：**尚未证明**。

一次观察到“最终退出”，只覆盖了一种调度和依赖行为。若 DB 永久阻塞、channel 无人接收或取消没有传入依赖，该 goroutine 仍可能无限存活。

缺失观测包括：依赖永久阻塞时能否取消、每条错误路径是否退出、多次请求后 goroutine 数是否持续增长，以及服务关闭是否等待或终止后台工作。

### 2. Handler 响应所有权与测试设计

#### 2.1 先修正测试模型

题目提示中“queue 到达阻塞点后，测试等待 handler 返回，再释放 queue”不能直接用于正确的同步 handler：handler 正在等待 `Queue.Write`，测试又等待 handler，二者会死锁。

应拆成两个模型：

- **同步 Queue 测试**：queue 阻塞时取消请求，断言 handler 因 `ctx.Err()` 返回且只写一次错误响应。
- **旧代码 late write 测试**：让异步 DB goroutine 停在写响应之前；handler 的 Kafka 路径完成并返回后，再放行 DB goroutine，稳定复现晚写。

#### 2.2 推荐的消费者接口与 handler 边界

```go
type Queue interface {
	Write(ctx context.Context, msg []byte) error
}

type TaskRepository interface {
	Insert(ctx context.Context, task Task) error
}

type Handler struct {
	queue Queue
	repo  TaskRepository
}
```

推荐的不变量是：**handler goroutine 是 `ResponseWriter` 的唯一所有者；依赖只返回结果，永远不接收 `ResponseWriter`。**

一个最小同步版本可以是：

```go
func (h *Handler) PostTask(w http.ResponseWriter, r *http.Request) {
	// 省略解码和校验。
	task := Task{ID: "task-1"}

	if err := h.repo.Insert(r.Context(), task); err != nil {
		http.Error(w, "internal error", http.StatusInternalServerError)
		return
	}
	if err := h.queue.Write(r.Context(), []byte(task.ID)); err != nil {
		http.Error(w, "failed to enqueue task", http.StatusInternalServerError)
		return
	}

	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(http.StatusAccepted)
	_ = json.NewEncoder(w).Encode(task)
}
```

这个版本容易测试，但 DB 成功、Kafka 失败时会留下不一致状态。生产设计至少应把任务标为 `enqueue_failed`/`pending` 并允许补偿重试；不能把两个外部系统误当作一个原子事务。

#### 2.3 可控 fake queue

```go
type blockingQueue struct {
	ready   chan struct{}
	release chan struct{}
	err     error
}

func (q *blockingQueue) Write(ctx context.Context, _ []byte) error {
	close(q.ready) // fake queue 负责关闭，表示已经进入阻塞点
	select {
	case <-ctx.Done():
		return ctx.Err()
	case <-q.release:
		return q.err
	}
}
```

channel 责任：测试创建全部 channel；fake queue 关闭 `ready`；测试关闭 `release`；没有任何 channel 被重复关闭。取消测试中不需要关闭 `release`，因为 `cancel()` 会使 fake 返回。

取消测试骨架：

```go
func TestPostTask_CancelWhileQueueBlocked(t *testing.T) {
	q := &blockingQueue{
		ready:   make(chan struct{}),
		release: make(chan struct{}),
	}
	h := newTestHandler(q)

	ctx, cancel := context.WithCancel(context.Background())
	req := httptest.NewRequest(http.MethodPost, "/tasks", validBody()).WithContext(ctx)
	rr := httptest.NewRecorder()
	done := make(chan struct{})

	go func() {
		defer close(done)
		h.PostTask(rr, req)
	}()

	<-q.ready
	cancel()
	<-done

	if rr.Code != http.StatusInternalServerError {
		t.Fatalf("status=%d, want %d", rr.Code, http.StatusInternalServerError)
	}
}
```

更成熟的 API 会把 `context.Canceled` 映射成内部日志/指标，并避免在客户端已经离开后依赖响应码表达结果；这里的核心验收是阻塞点响应取消且 handler 能退出。

queue 失败测试只需在 `<-q.ready` 后设置既定错误并 `close(q.release)`，等待 `done`，再断言仅有一个失败响应。成功测试则令 `err == nil`，断言 `202`。

#### 2.4 记录写入顺序的测试替身

```go
type responseEvent struct {
	kind string
	code int
	body string
}

type recordingWriter struct {
	mu     sync.Mutex
	header http.Header
	events []responseEvent
}

func newRecordingWriter() *recordingWriter {
	return &recordingWriter{header: make(http.Header)}
}

func (w *recordingWriter) Header() http.Header { return w.header }

func (w *recordingWriter) WriteHeader(code int) {
	w.mu.Lock()
	defer w.mu.Unlock()
	w.events = append(w.events, responseEvent{kind: "status", code: code})
}

func (w *recordingWriter) Write(p []byte) (int, error) {
	w.mu.Lock()
	defer w.mu.Unlock()
	w.events = append(w.events, responseEvent{kind: "body", body: string(p)})
	return len(p), nil
}

func (w *recordingWriter) snapshot() []responseEvent {
	w.mu.Lock()
	defer w.mu.Unlock()
	return append([]responseEvent(nil), w.events...)
}
```

测试旧代码的 late write 时，异步 DB fake 关闭 `ready` 后等待 `release`；Kafka 路径先返回。测试等待 handler `done`，保存 `before`，关闭 `release`，等待 DB goroutine `dbDone`，再保存 `after`。若 `len(after) > len(before)`，就稳定证明了 handler 返回后的越界写入。

注意：这类测试需要先把真实 DB/Kafka 获取方式改为依赖注入，才能放置同步点。当前 `GetInstance` 与函数内部 `go func` 把依赖和生命周期写死，正是难以测试的设计信号。

### 3. Context 取消契约

| 阻塞点 | 应使用的 context | 取消来源 | 取消后的错误去向 | 是否允许继续 |
|---|---|---|---|---|
| Kafka 写入 | 请求内入队使用 `r.Context()` | 客户端断开、请求 deadline、服务上游取消 | handler 记录分类后的错误；未提交响应时返回失败 | 调用应停止等待，但消息可能已写入，不能视为回滚 |
| DB 插入（同步请求内） | `r.Context()` | 同上 | 返回 handler，由 handler 唯一决定响应 | 不继续；依赖必须支持 `Context` |
| DB 插入（真正异步） | 服务级 worker context | 服务关闭、任务 deadline | 更新任务状态、日志和指标，不写 HTTP | 可脱离请求继续，但由 worker 管理 |
| HTTP 响应写入 | 不额外启动 goroutine；由 handler 串行写 | handler 控制流 | 写失败只能记录，不能再尝试第二套响应 | handler 返回后绝不继续写 |

当前风险：`DbService.InsertTask(task)` 不接收 context，而且运行在未被等待的 goroutine 中。客户端取消不会通知它，服务关闭也无法确认它何时结束。

最小改造边界：

```go
type TaskRepository interface {
	Insert(ctx context.Context, task *Task) error
}
```

若 DB 插入属于请求成功的必要条件，就同步调用 `Insert(r.Context(), task)`；若业务要求先返回 `202` 再持久化，则把不可变任务数据投递给服务级有界队列，由 worker 使用服务 context 处理，并提供任务状态查询。不要为每个请求创建一个无人管理的 goroutine。

这里与 408 网络知识的联系是：超时或连接断开只能说明通信结果不确定，不能证明对端未执行。context 也是本地协作式取消机制，不是跨系统事务回滚协议。

### 4. 最短不同值窗口

目标：在 `nums=[1,2,1,3,2]` 中找到至少包含 3 个不同值的最短连续窗口。

窗口不变量：在每次扩张或收缩完成后，`counts[x]` 等于 `x` 在闭区间 `[left,right]` 中的出现次数，`distinct` 等于其中频次大于 0 的键数量。

关键状态：

| 动作 | `left` | `right` | `distinct` | `minLen` | 说明 |
|---|---:|---:|---:|---:|---|
| 加入 `1` | 0 | 0 | 1 | 6 | 不满足 |
| 加入 `2` | 0 | 1 | 2 | 6 | 不满足 |
| 加入 `1` | 0 | 2 | 2 | 6 | `1` 的频次变为 2 |
| 加入 `3` | 0 | 3 | 3 | 4 | 首次满足 |
| 删除左侧 `1` | 1 | 3 | 3 | 3 | 仍满足，窗口 `[2,1,3]` |
| 删除左侧 `2` | 2 | 3 | 2 | 3 | 不再满足，停止收缩 |
| 加入 `2` | 2 | 4 | 3 | 3 | 再次满足，窗口 `[1,3,2]` |
| 删除左侧 `1` | 3 | 4 | 2 | 3 | 不再满足 |

答案为 `3`。由于三个不同值至少需要三个位置，不可能再缩短。

表驱动测试项：

```go
{
	name: "shrink then expand again",
	nums: []int{1, 2, 1, 3, 2},
	k:    3,
	want: 3,
},
```

复杂度证明：`right` 只从左向右移动 `n` 次；`left` 也只向右移动，最多 `n` 次。每次移动进行均摊 `O(1)` 的 map 操作，所以总时间复杂度是 `O(n)`，不是看到两层循环就判断为 `O(n²)`。map 最多保存 `u` 个不同值，空间复杂度为 `O(u)`，且 `u <= n`。
